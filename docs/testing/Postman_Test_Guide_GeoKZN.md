# Тестирование GeoKZN через Postman

Да, в твоем случае `Postman` подходит очень хорошо, потому что у проекта есть отдельный `backend API`, и через него можно проверить:

- регистрацию и авторизацию;
- создание и чтение событий;
- работу комментариев;
- жалобы;
- административные функции;
- обработку ошибок и блокировок.

Важно: `Postman` тестирует именно **серверную часть и API**.  
Для главы `Тестирование ПО` это нормально и даже удобно. Но для полноты лучше потом дописать, что **пользовательский интерфейс мобильного клиента проверялся вручную** на телефоне через Expo Go.

## 1. Что нужно запустить перед тестами

### Frontend

Для Postman запуск клиента не обязателен, потому что тестируется API.  
Но если хочешь параллельно смотреть интерфейс приложения:

```powershell
cd "E:\Курсовая\TestApp"
npm run start
```

## 3. Как импортировать коллекцию в Postman

1. Открыть `Postman`.
2. Нажать `Import`.
3. Выбрать файл `GeoKZN.postman_collection.json`.
4. После импорта открыть коллекцию `GeoKZN API Tests`.
5. Проверить переменную `baseUrl`.

Значение по умолчанию:

```text
http://localhost:4000
```

Если backend запущен на другом IP, нужно заменить адрес.

## 4. Порядок запуска тестов

Рекомендуемая последовательность:

1. `GET report reasons`
2. `GET event types`
3. `POST register user A`
4. `POST login user A`
5. `POST create event by user A`
6. `POST comment by user A`
7. `POST register user B`
8. `POST login user B`
9. `GET events by user B`
10. `GET comments of event by user B`
11. `POST report event by user B`
12. `POST login admin`
13. `GET admin reports`
14. `GET admin users by nickname`
15. `POST block user A for 60 min`
16. `POST unblock user A`
17. `POST reject first report`
18. `POST invalid login`
19. `POST invalid event without title`

## 5. Что делает коллекция

Коллекция автоматически сохраняет переменные:

- `userAToken`
- `userBToken`
- `adminToken`
- `userAId`
- `userBId`
- `eventId`
- `commentId`
- `reportId`
- `reportReasonId`

То есть тесты связаны между собой и подходят для демонстрации последовательного сценария работы системы.

## 6. Что можно написать в главе тестирования

Для диплома или отчета можно оформить так:

### Цель тестирования

Цель тестирования заключалась в проверке корректности работы серверной части информационной системы GeoKZN, обработке входных данных, проверке прав доступа пользователей, а также подтверждении корректности выполнения основных бизнес-сценариев.

### Используемый инструмент

Для тестирования API использовалось приложение `Postman`, позволяющее формировать HTTP-запросы к backend-серверу, выполнять проверку ответов и автоматизировать часть тестовых сценариев с помощью встроенных тестов.

### Проверяемые сценарии

- регистрация пользователя;
- авторизация пользователя;
- создание события;
- добавление комментария;
- просмотр списка событий;
- просмотр комментариев;
- отправка жалобы;
- работа административной панели;
- блокировка и разблокировка пользователя;
- обработка ошибочных запросов.

Можно вставить в главу вот такую таблицу.

| № | Сценарий | Входные данные | Ожидаемый результат | Фактический результат |

| 1 | Регистрация пользователя | username, password | Создан новый пользователь, возвращен токен | Успешно |

| 8 | Отправка жалобы | targetType, targetId, reasonId | Жалоба сохраняется в системе | Успешно |

## 8. Что еще можно добавить в текст

Хорошая формулировка для отчета:

> В ходе тестирования было установлено, что backend-сервер корректно обрабатывает как штатные, так и ошибочные сценарии использования. ## 9. Ограничение метода

Важно честно указать:

> Следует отметить, что использование Postman позволяет протестировать серверную часть и API-интерфейсы, однако не заменяет полного тестирования пользовательского интерфейса мобильного приложения. Поэтому дополнительно проводилось ручное тестирование работы клиента на мобильном устройстве.
